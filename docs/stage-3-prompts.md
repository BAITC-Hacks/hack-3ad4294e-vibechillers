# Stage 3 — execution prompts

Run each prompt in the named participant's **main session** using **GPT-6 Astra / high / fast 1.5×**. All three workstreams start concurrently after receiving the handoff commit. Main-session selection does not change application inference or automatically override subagent models. `scout` on Batyrkhan's configured machine resolves through `@lookup` to `openai-codex/gpt-6-sol:xhigh`; `.omp/` is ignored, so teammates must not assume this routing arrived through Git.

These prompts implement [the active plan](stage-3.md); they do not reopen Stage 1/2. The ownership cutover is explicit: **Batyrkhan = backend/contracts/dependencies; Alibi = eval/fixtures/quality; Askat = frontend/export/delivery**. Stage 4 is release acceptance, not another feature round. The official weights are 25/25/25/15/10; all five must-haves remain required.

## Batyrkhan — backend, agent and integration

```text

Проверь текущую ревизию и локальные изменения; синхронизируйся без потери чужой работы. Не читай holdout-ответы, hold-* фикстуры или исходник генератора, содержащий held-out gold, ради настройки ядра.

Твоя зона: apps/api/app/, общие контракты, корневая runtime-конфигурация и зависимости/lockfiles. В Stage 3 apps/web/ принадлежит Аскату: не редактируй frontend параллельно с ним. Алиби владеет eval/kt/, seeds/kt/eval/ и quality evidence. Изменения их контрактов передавай через коммит и точный handoff.

Первое действие разработки: зафиксируй целевые Pydantic-схемы из §4 плана и поведение HTTP/SSE, сообщи ревизию Алиби и Аскату. Сохрани существующие function statuses, ClauseRef/Citation, POST/GET /audits и один terminal event. Добавь unit_changes, risks, agent execution status и source locations без второго несовместимого формата отчёта. Старые сохранённые отчёты открываются, но отсутствие нового поля не означает отсутствие риска.

Затем реализуй три независимых backend-среза параллельно через builder-агентов с непересекающимися файлами:
1. Настоящий ограниченный audit-agent: переиспользовать state machine agent/loop.py, llm adapter и typed registry; модель выбирает read/search/context/proposal инструменты по предыдущим результатам. Не оставлять фиксированный двухфазный pass главным агентным путём. Host выполняет первоначальный parse/align; модель не может сбрасывать findings. Сохрани run-scoped доступ, resolve_alignment/_decision_problem, проверку цитат, 12 turns / 32 calls / 180 seconds и per-call timeout. Кандидаты из поиска не становятся принятыми соответствиями без проверки. API остаётся единственным владельцем последовательности и сохранения audit events; не вкладывай один trace writer в другой.
2. M1 и M3: сохранившиеся/созданные/реорганизованные подразделения с доказательствами; межподразделенческое дублирование и потенциальные конфликты интересов. Переиспользуй _unit_rows и ответственность/контекст Stage 2. Не подменяй подразделение упомянутой ролью, похожий текст — конфликтом, перенос/merge — потерей. Для overlap без before-пункта используй Risk, не выдумывай предшественника. Потенциальный конфликт — обоснованный риск, не утверждение нарушения закона.
3. Входные данные: доведи существующий DOCX/PDF/XLSX путь до смыслового разбора приложений и точных источников. Не добавляй новый парсер или сервис без необходимости. Не выдумывай страницы Word, координаты или поддержку произвольных диаграмм. Пустое/нечитаемое приложение должно явно объясняться пользователю.

Ты лично владеешь models.py, общей оркестрацией, разрешением пересекающихся изменений и интеграцией. Builders не устанавливают зависимости и не запускают общие tests/build/lint во время параллельных изменений. После реализации независимый reviewer/demo-auditor ищет фальшивые tool calls, gold leakage, неподтверждённые выводы и пропущенные части ТЗ. Воспроизводимые дефекты исправляй, не маскируй.

Не жди окончательной human-разметки, чтобы использовать синтетические control inputs Алиби для разработки; но не выдавай предварительные ожидания за независимую точность. Сравнение качества выполняет Алиби на той же ревизии. До paid API, отправки исходных документов или deployment получи точное разрешение на provider/model, данные, лимит и доступ. Подписка Astra не является API-ключом приложения. При отсутствии разрешения закончи локальную реализацию и обозначь конкретный заблокированный live-gate; не подставляй mock вместо успеха.

Готовность: §11 control bundle действительно проходит через API и совместно с Аскатом через UI; модель выбирает инструменты, использует результат и делает проверяемый вывод/воздержание; M1–M5 и форматы доступны; trace и Report сохраняются; invalid output/timeout/limit дают честный fallback/partial, не ложный completed. Существующая регрессия не ломается; рост обоснованных abstentions сам по себе не ошибка. Один согласованный интеграционный прогон после сборки срезов, реальные команды и результаты в tracked evidence.

Перед каждым коммитом git pull --rebase --autostash; фиксируй только свои пути, без чужого незавершённого кода, секретов и force push. Для передачи общей ревизии используй согласованный командой push. Верни: коммиты, что реально работает, воспроизводимые команды, результаты, ошибки/ограничения и точный handoff Аскату/Алиби. Не завершай работу на плане, scaffold или неподключённом агенте.
```

## Alibi — independent evaluation, control data and adversarial review

```text
Ты — владелец независимой проверки качества Function Lineage Auditor. Работаешь в main-сессии на GPT-6 Astra high fast 1.5×. Stage 2 завершён; реализуй проверочный модуль Stage 3 с тяжёлой параллельной проверкой источников, а не очередной таблицей красивых процентов.

Прочитай seeds/kt/TASK.md, docs/stage-3.md, docs/evidence/kt-quality.md, eval/kt/HANDOFF.md, правила selection/split/reviews существующего evaluator. Сначала проверь ревизию и сохрани локальную работу при синхронизации. Твоя зона: eval/kt/, seeds/kt/eval/, docs/evidence/kt-quality.md. Не редактируй apps/**, README, зависимости или чужие delivery-файлы. Backend/contracts принадлежат Батырхану, frontend/export — Аскату.

Первый приоритет — сразу выдать обоим runnable control inputs из §11 ТЗ: реорганизация подразделения, потеря функции и дублирование. Добавь положительный potential-conflict случай и отрицательный пример допустимого сотрудничества. Используй явно синтетический набор под seeds/kt/eval/control/, не выдавай его за документы организатора. Подготовь Word/PDF/Excel представления, хеши, источники и предварительные ожидания до просмотра нового ответа системы. Inputs доступны для разработки сразу; подтверждённые метрики требуют принятого gold. Не блокируй разработку ожиданием проверки всего holdout.

Сохрани исходную regression.jsonl, версии challenge и историю исправлений. pending_human остаётся pending_human, пока человек не подтвердил: согласие двух ИИ не заменяет человеческую проверку. Независимых reviewer-агентов раздели на источник/структуру, обязанности/конфликты и техническую целостность. Они сначала получают исходники, целевые refs и контракт, без текущих ответов системы. Один владелец gold вносит решения и сохраняет разногласия. Holdout хранится отдельно; не передавай его ответы Батырхану или Аскату, не используй их для tuning, не оценивай до approval gate.

Получив schema commit Батырхана, расширь существующий scorer и capture, не создавай второй evaluator. Function labels остаются на прежних семи статусах; unit_changes и risks оцениваются отдельно. Согласуй новый label shape до capture. Защити точные refs/quotes, правильную сторону документа, N:M, source locations, одинаковые bytes с разными aliases, различие reviewable risk и доказанного нарушения. Отрицательные примеры должны ловить ложные duplicate/conflict/missing. Не импортируй private alignment helpers и не получай expected answers из системы.

Тяжёлые независимые срезы запускай параллельно: подготовка source-first controls, расширение evaluator, независимый review gold/семантики. Дай каждому непересекающиеся файлы; freeze интерфейса — твоя ответственность. Подагенты не ставят зависимости и не запускают общий build/lint/test на незавершённых соседних изменениях. Затем один интеграционный прогон владельца.

Измерь deterministic и настоящий agent на одинаковых байтах и одной интегрированной ревизии, при согласованном provider/data/spend. Используй публичный API и сохраняй реальные Report/trace, без replay/mock вместо inference. Отдельно проверь result-dependent tool actions, не только наличие tool_call событий. Зафиксируй конфигурацию модели, успешные/partial/fallback запуски, число реально рассмотренных случаев, TP/FP/FN/abstentions, валидность цитат и неоценённую область. Голосование reviewer-агентов не является точностью продукта. Старые 6/12 и 6/10 относятся к прежнему ядру и проекту gold — не сравнивай их с новой версией как чистый эксперимент.

Сохрани appropriate abstention отдельным показателем. 0/0 — N/A. 37 unresolved refs не равно 37 findings. Если не хватает доступа к live model, закончи evaluator, controls и независимую проверку локально, обозначь точный missing prerequisite; не публикуй выдуманные agent-метрики. Неподтверждённые labels могут иметь только явно provisional результаты.

Готовность: воспроизводимые control inputs и источники, evaluator для всех обязательных выходов, контроль ухудшения scorer, прозрачная версия gold и согласованное сравнение двух режимов. Краткий development-only error brief Батырхану; безопасные демонстрационные inputs Аскату; итоги в tracked kt-quality.md. Не публикуй ключи или сырые чувствительные trace.

Перед каждым коммитом git pull --rebase --autostash; фиксируй только свои пути. Передавай коммит inputs ранним handoff, не держи всё до финальной оценки. Push — по согласованному режиму команды, без force. В конце перечисли коммиты, команды, raw counts/denominators, подтверждения/разногласия, блокеры и то, чего измерение не доказывает. Не завершай на одном плане или mock-отчёте.
```

